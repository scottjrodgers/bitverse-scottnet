# Review: doc-set audit, August 2026

**Status:** working document, **not normative**. It binds nothing. Retire it when Part 3 is
all-closed, the way `design-review.md` was retired into `reference/rationale.md` §13.

**Scope.** Three passes over the eight documents in `docs/` plus
`scripts/policy/corp/recipes.js`, looking for duplication, contradiction, and normative text
that cannot be implemented without guessing. Fifty-seven findings, all cited to file and
section.

**How to use it.** Part 1 is eight questions that need a human decision; nothing else should be
touched until they are answered, because most of the mechanical fixes depend on the answers.
Part 2 is the inventory. Part 3 tracks disposition.

**One caveat about Part 1.** These questions surfaced because the specification has never been
implemented. Every one of them would have been answered in an afternoon of writing the Director
and hitting the wall. Answering them on paper first is defensible — but the cheaper path may be
to answer only Q1–Q3, write 300 lines, and let the code settle the rest.

# Part 1 — Eight questions the design has to answer

Each is a **model** question: the answer changes the shape of the specification, not just its
wording. They are ordered so that earlier answers constrain later ones.

---

## Q1. Is RAM one resource, or one resource per host?

**The contradiction.** `strategy.md` §5 defines a resource id as `kind:instance` "where instances
exist", giving `ram:home` and `ram:pserv-0` as examples. §7's lease rows agree —
`"resource": "ram:pserv-0"`. But §6.1's candidate example asks for `"requires": { "ram": 4096 }`,
a bare name. A candidate cannot be matched to a lease if the two disagree about what a RAM
resource *is*.

**Why it is a model question.** It decides whether a controller knows that hosts exist.

| | |
|---|---|
| **(a) Per host** | Candidates name a host: `requires: { "ram:pserv-0": 4096 }`. But a hacking controller does not care *which* host — it wants 4096 GB anywhere. This forces every controller to enumerate the fleet and publish a candidate per host, which is combinatorial and puts infrastructure knowledge in the wrong layer. |
| **(b) One fungible pool** | Candidates ask for `ram: 4096` and the lease says the same. Simple, and wrong at the point of use: `ns.exec` needs a host name. Somebody has to place the work, and nothing in the spec does. |
| **(c) Fungible request, placed grant** | Candidates ask for `ram: 4096`. The Director does the bin-packing and issues **several** lease rows — `ram:pserv-0: 2048`, `ram:home: 2048`. |

**Recommendation: (c).** It is the only option under which both existing examples are already
correct: §6.1's bare `ram` is what a controller *asks* for, §7's `ram:pserv-0` is what the
Director *grants*. Placement is exactly an allocator's job, and it does not violate §0 — a host
is a resource instance, not a game mechanic.

**What it costs.** The Director needs a bin-packer, and a controller must handle a grant that
arrives as a set of hosts rather than a number.

**The follow-on nobody has noticed.** An HWGW batcher needs a whole batch to fit somewhere.
Granted 4096 GB spread across eight hosts at 512 each, it may be unable to launch a single batch
of 600 GB. A fungible request therefore needs a granularity term — `requires: { ram: 4096,
minPerHost: 600 }` — or the Director will hand out budgets that satisfy the number and cannot be
used. **This is the first thing an implementation will hit, and it is not in the spec.**

---

### DECIDED — 2026-08-25: option (c), with placement split across two layers

**A fungible request; one or more grants.** A controller asks for an amount of `ram` and does
not name hosts. The Director replies with a set of `(host, gb)` lease rows.

**Two placement functions, at two levels, with different objectives.**

| | Director-side | Controller-side |
|---|---|---|
| Question | which hosts satisfy this grant? | where does *this script* go? |
| Unit | a lease, held for minutes to hours | one process, launched now |
| Objective | **fewest hosts; avoid leaving small unusable remainders** | pack efficiently inside what is already held |
| Input | fleet inventory minus grants already issued | this controller's own lease and its own usage |
| Never | reads live free RAM | reads live free RAM, or anything outside its lease |

The second is the "deploy anywhere it fits" abstraction from the pre-consolidation scripts,
which is worth carrying forward — with its input rebased from *the fleet* to *this controller's
lease*. That is the whole change: a shared library is not a lock, so two controllers each
computing fleet-wide free RAM in the same tick both claim it. Bounded to a lease, the same
code is safe because no two leases overlap.

**State the Director's objective precisely; "best fit" is ambiguous.** Applied to the whole
request — the smallest single host that fits it — best-fit *consolidates*, which is wanted.
Applied greedily chunk by chunk, it fills the smallest adequate host first and hands back a pile
of slivers, which is not. Both are "best fit" in ordinary usage and the second is the easier
thing to write. The specification must say which, because the wrong one produces a lease that
satisfies its number and cannot run a single batch.

### What (c) obliges, that the documents do not yet contain

1. **The Director's "free" is bookkeeping, never observation.** Free RAM on a host is fleet
   inventory minus the grants the Director has itself issued against it. It must not call
   `getServerUsedRam`; doing so re-opens the race the lease model exists to close. Note this is
   neither `granted` nor `held` — `held` is the consumer's report of its *own* usage (§7.2) and
   is not an input to allocation.
2. **Somebody must publish the fleet inventory, and nobody does.** §8.1 forbids the Director
   from calling game APIs; it assembles a world view from controller state files only. Which
   hosts exist and how much RAM each has therefore has to arrive from an `infra` controller's
   state file. **There is no `infra` controller and no inventory schema.** This is a new
   requirement created by this decision.
3. **Reconciliation is required, as a report and not a correction.** Bookkeeping drifts from
   reality — a script run from the terminal, a server deleted, a manager killed mid-drain. A
   periodic check comparing each host's actual used RAM against the sum of `held` against it,
   logging drift, is what makes an unobserved allocator trustworthy. It must only report:
   a corrector racing the consumers reintroduces the original problem.
4. **`minPerHost` (or an equivalent) joins the candidate schema**, so a granularity requirement
   the fleet cannot satisfy fails loudly instead of producing an unusable lease.

**Sections to change when this lands:** `strategy.md` §5 (resource identity — request form vs
grant form), §6.1 (`requires`, plus `minPerHost`), §7.2 (a lease is a set of rows, not one),
§8.1 (inventory is a world-view input). New: an `infra` controller state schema, and the
reconciliation report.

## Q2. Does the horizon gate apply to leases, or only to purchases?

**The gap.** `strategy.md` §6.5 step 3 admits a candidate if `paybackSec < horizon || permanent`.
`paybackSec` is not a field on either candidate shape in §6.1, is not derived anywhere, and
appears in no other normative document. Its only definitions in the repo are inside the retired
`wants` schema, quoted in past tense.

**Why it is a model question.** Payback is a property of *spending*. Money spent on a server is
gone at install; RAM leased is borrowed and returned. Asking a lease for its payback period may
be a category error, in which case the gate applies to half the candidates and the spec should
say so.

| | |
|---|---|
| **(a) Purchases only** | Define `paybackSec = cost.money / produces.ratePerSec` for purchase candidates. Production candidates skip step 3. Honest and simple. |
| **(b) Both, defined per kind** | Purchase: seconds to recoup the spend. Production: `transition.startSec` — seconds before the lease produces anything. Then step 3 stays one uniform rule. |

**Recommendation: (b).** It covers a case (a) silently gets wrong: starting a four-minute HWGW
prep sixty seconds before an augmentation install is pure waste, and under (a) nothing stops it.
The two definitions are different quantities under one name, so the spec must state both
explicitly rather than leaving "payback" to intuition.

---

### DECIDED — 2026-08-25: option (b), one gate, two definitions

The horizon gate in §6.5 step 3 applies to **every** candidate. `paybackSec` is defined per
candidate kind, and the specification must give both definitions rather than one word:

| Kind | `paybackSec` | Meaning |
|---|---|---|
| `purchase` | `cost.money / produces.ratePerSec` | seconds to recoup the spend |
| `production` | `transition.startSec` | seconds before the lease produces anything |

These are **different quantities under one name**, which is why leaving it to intuition was
producing two incompatible readings. Write both into §6.1 as derived fields and state in §6.5
that the gate reads whichever applies.

**What this buys:** the gate now refuses to start a four-minute HWGW prep sixty seconds before
an install. Under a purchases-only gate nothing would have stopped it, and the loss is silent —
the prep simply never pays off and the RAM was spent on nothing.

**Open sub-questions this leaves**, both minor and both for the §6.1 edit:

- `produces.ratePerSec` is `0` or the produced path is not money for some purchase candidates.
  `paybackSec` is then `Infinity`, so the gate rejects unless `permanent == true`. That is
  probably correct behaviour, but state it rather than letting a division produce it.
- A `production` candidate with no `transition` block. Default `startSec` to `0` (available
  immediately, always admissible) rather than treating a missing field as unknown.

## Q3. Where do `advisoryMode` and per-controller `enabled` live?

**The gap.** `manager-contract.md` depends on both: §6 step 4 branches on `advisoryMode`, §6a
defines the durable pause as `director.json → subsystems.<name>.enabled = false`, and §2 lists
them as standing directives. `strategy.md` §7's authoritative `director.json` has neither field —
and says "the Director is its only writer", so a human could not set them there anyway.

This is the substance behind the contradiction already flagged in `START-HERE.md` §5.2. It is
not a naming drift: **there is currently no mechanism for advisory mode or for pausing a
controller.**

| | |
|---|---|
| **(a) Add them to `director.json`** | Smallest edit. But it makes the Director's output file also a human input file, breaking single-writer — the one rule the whole state design rests on. |
| **(b) Express both as constraints** | `constraints.json` is already human-writable and already the home of hard boundaries. A disabled controller becomes `{"kind":"disable","controller":"corp"}`. |
| **(c) A third file, `/state/control.json`** | Clean separation: goals = what, constraints = boundaries, control = operator switches. One more file to explain. |

**Recommendation: (b).** "Do not allocate to corp" is precisely a hard boundary, and
`constraints.json` costs nothing new. Note one semantic difference to decide alongside it:
`forbid` prevents *approval*, whereas `manager-contract.md` §6a's disabled manager **keeps
running and keeps writing its state file**, reporting `health: "blocked"`. Those produce the
same allocation outcome but different observability, and the idling behaviour is the one worth
keeping — it is what lets you toggle a subsystem without fighting the watchdog.

`advisoryMode` is a genuinely different thing: it wants approvals *granted and logged* but not
acted on. It is an execution switch, not an allocation switch. Put it in `constraints.json` as a
global flag and let each controller read it, but do not model it as a `forbid`.

---

### DECIDED — 2026-08-25: three switches, not two — (b) and (c) together

**The options above were framed wrongly and the recommendation was half wrong.** They asked
*which file*, when the question that decides it is *at which point in the pipeline does each
switch act*. Answer that and the filing is obvious. The original recommendation also proposed
modelling `advisoryMode` as a `forbid`, which is incorrect: a `forbid` fires at §6.5 step 2,
inside the allocator, which is precisely where advisory mode must not interfere.

Separating by pipeline position shows there are **three** switches, not two:

| Switch | Acts at | Semantics | Home |
|---|---|---|---|
| `disable` a controller | **allocation** | its candidates are never ranked; its leases drain by the normal `requested → 0` path; its resources are reallocated | `constraints.json` |
| `pause` a controller | **execution** | keeps its lease, takes no actions, keeps writing its state file, reports `health: "blocked"` | operator switches |
| `advisoryMode` | **execution** | plan normally, log the intended action list, execute nothing | operator switches |

**Why `disable` and `pause` are not one switch.** The old `subsystems.<name>.enabled` did both
jobs and neither well. They differ in what happens to the held resources:

- *Disabled* returns them to the pool. Re-enabling means re-competing and paying the
  `transition` cost again (§7.3). Correct for "I am not building corp this run."
- *Paused* holds them. Instant off, instant on, no re-prep — correct for debugging, which is
  what `manager-contract.md` §6a describes it for. But a paused controller sits on its grant
  producing nothing **and the Director cannot see this**: it reads `held`, finds the resource in
  use, and never reallocates. A forgotten pause is an invisible, unbounded waste.

**Why `advisoryMode` cannot be a constraint.** If advisory mode stopped the *Director* from
publishing directives, the run would show nothing about what it would have decided — defeating
the purpose. The Director must allocate normally and write its full decision record (§9); the
*controllers* are what stop. That makes it execution-side by construction, and not expressible
as an allocation constraint.

**Why the third file earns its place.** The doc set has `goals.json` (what should become true)
and `constraints.json` (what may not happen), and no home for *how the machinery itself should
behave right now*. That is a real third category, not a filing convenience.

**Two refinements:**

1. **`pause` must be loud.** It is the right first move when something looks wrong — faster and
   safer than killing a script — but its cost is silent. Surface it prominently, and decide
   whether it expires rather than persisting until somebody remembers.
2. **`advisoryMode` needs a per-controller form.** `manager-contract.md` §4 calls it "the main
   way new managers are validated," and validating a new controller means running *it* in
   advisory while everything else executes. Global flag plus per-controller override.

**Sections to change when this lands:** `strategy.md` §4.1 (a `disable` constraint kind), a new
section for the operator-switch file; `manager-contract.md` §2 (the files/ports table), §4
(remove the stale schema entirely — see C1–C4), §6 step 4, §6a (split the durable pause into
`disable` and `pause`).

## Q4. How does a `forbid` constraint match a candidate?

**The gap.** `strategy.md` §4.1 gives `{"kind":"forbid","action":"installAugmentations"}` and
`{"kind":"forbid","action":"joinFaction","match":{"type":"city"}}`. §6.5 step 2 says "discard
candidates violating any `forbid` constraint". But §6.1's candidate schema has no `action` field
and no `type`. **Both worked examples in the specification are unimplementable against its own
schema.**

**Recommendation: add an optional `action` string and an optional `tags` object to the candidate
schema, and define `match` as exact key/value comparison against them.**

This does not violate §0. The *controller* names the action; the Director only compares strings
and never interprets them — the identical trick that makes `produces.path` work. Anything else
(matching on id globs, inferring from `kind`) is guessing, and two implementers will guess
differently.

## Q5. What does a candidate for an exclusive resource look like?

**The gap.** §5 lists `exclusive` as one of four resource kinds (`player`, `sleeve:3`). §7.4 says
exclusive resources are assigned, and §7's `assignments: {"player": "faction-work:NiteSec"}`
shows the output. §6.1 shows only `production` and `purchase` candidates. **Nothing specifies
where the string `"faction-work:NiteSec"` comes from.** The document's own leading example —
sleeves committing homicide to produce karma — cannot be expressed.

| | |
|---|---|
| **(a) A third `kind: "assignment"`** | Explicit, and a third shape to specify, test and maintain. |
| **(b) Reuse `production`** | `requires: { "player": 1 }` plus a new `activity` field carrying the opaque string that lands in `assignments`. |

**Recommendation: (b).** A production candidate already means "give me this resource and I will
produce at this rate". The player's body is just a resource with a count of one. Two candidate
kinds beat three, and §7.4's "assignments hold until the next round" already describes the
lifecycle.

## Q6. Are tiers mutually exclusive, and how does the allocator know?

**The gap.** §6.1 says controllers advertise tiers so the allocator can pick "the tier that
fits". §6.5's greedy loop has no notion of a candidate family. Nothing prevents
`hwgw:phantasy:t1` (512 GB) and `hwgw:phantasy:t2` (4096 GB) from both clearing the gate and
both being granted — **double-counting one controller's production and over-leasing it 4608 GB
to do a 4096 GB job.**

**Recommendation: add an explicit `group` field.** At most one candidate per group is allocated
per resource per round. The alternative — stripping a `:tN` suffix by convention — is an
unwritten rule that will be violated the first time somebody names a candidate differently, and
it fails silently.

`group` also generalises past tiers: two genuinely different strategies for the same goal are
mutually exclusive for the same reason.

---

## Q7. What supplies the install horizon, without naming a goal?

**The gap.** §6.5 step 3 uses "the current install horizon". `rationale.md` §3 explains that
`timeToInstallSec` "became a goal deadline" — but no section says *which* goal supplies it, and
§0 forbids the Director from branching on a named goal, subsystem or mechanic.

**Recommendation: let a goal declare a role.** `{"id": "...", "role": "installHorizon", ...}` and
the Director uses that goal's deadline. Data-driven, exactly like `produces.path`, and it
degrades correctly: no goal carries the role, so there is no install horizon, and §6.5 already
says such candidates are admissible.

---

## Q8. How does the Director learn a purchase approval was taken up?

**The gap.** §7.1 covers only the unused case: "an approval that is never taken up expires at the
next allocation round." Nothing says how a *used* one-shot purchase leaves the ranking. A naive
implementation re-approves the same top-ranked candidate every round and **double-spends.**

| | |
|---|---|
| **(a) It falls out of convergence** | The controller buys, its target state is now met, so it stops advertising the candidate. No new mechanism. Vulnerable to a tick of lag: the Director can re-approve before the controller's next state write. |
| **(b) Explicit acknowledgement** | The controller lists executed candidate ids in its own state file. The Director skips those. |

**Recommendation: (a) as the model, (b) as the interlock.** Convergence is the right story and
should stay the story; the `executed` list is three lines of defence against a race that costs
real money. The consumer writes it, so single-writer ownership is preserved.
